# 评分契约

RolePilot 的评分协议用于生成可解释的练习反馈。模型负责理解回答并给出结构化判断，程序负责验证证据、换算分数、合并追问和计算岗位维度结果。当前新会话使用 `practice-v1` 协议；用量记录使用 `usage-v1`。

## 评分输入

评估输入由题单元数据、当前回答与会话中的岗位量规组成。专业题使用 `role_profile.rubric`，动机题使用独立的两维量规；`rubric` 不存储在每一道题单记录中。主要字段包括：

| 字段 | 作用 |
|---|---|
| `content` | 当前面试题文本 |
| `question_kind` | 专业题或动机题 |
| `category`、`skills` | 题目对应的岗位主题和技能 |
| `depth_level` | concept、application 或 deep 等问题深度 |
| `rubric` | 当前题目允许评估的岗位维度及权重 |
| `difficulty` | 题目难度，用于后续难度调整和可选加权 |
| `plan_question_index` | 主问题与追问的归属，用于合并同一主题 |
| `project_ref`、`jd_ref`、`research_ref` | 简历项目、JD 要求和调研来源的溯源信息 |

这些字段帮助系统把问题绑定到岗位要求和候选人经历；来源和项目字段用于题目守卫、解释和追溯，不直接等同于分数。

## 模型输出

`assess` 节点要求模型返回结构化结果，包含：

JSON 输出采用提示词约束、解析和程序校验，未启用供应商原生 `json_schema` 响应模式。

- `scoreable`：本次回答是否有足够内容进行评分；
- `dimension_levels`：对当前量规维度给出的 1–5 档能力判断；
- `evidence`：支持判断的回答原话；
- `missing_points`：回答中仍缺少的要点；
- `hallucination_or_conflict`：是否出现与简历或题目事实冲突的内容；
- `next_action`：`follow_up`、`next_question`、`explain` 或 `end`，由程序转成受限的图路由；
- `confidence`：`low`、`medium` 或 `high`，表示模型对判断的信心。

## 程序校验

模型输出不会直接成为最终分数。程序会检查：

1. 必填字段和字段类型是否正确；
2. 维度键是否属于当前题目的岗位量规；
3. 档位是否为 1–5 的整数；
4. 证据是否确实来自当前回答原文；
5. 下一步动作是否属于允许的路由；

提交前，服务层另行校验题目版本与会话处理权；出题和追问阶段的岗位守卫检查题类、来源与岗位范围。这些约束与评分协议共同工作，职责分开。

协议非法、证据缺失或证据与当前回答不匹配时，该轮不会被程序补造成分。系统会保留失败原因，避免模型通过格式错误获得默认分数。

## 分数换算与聚合

档位采用以下固定映射：

| 能力档位 | 数值分 |
|---:|---:|
| 1 | 2 |
| 2 | 4 |
| 3 | 6 |
| 4 | 8 |
| 5 | 10 |

单题分数只对本题实际覆盖的量规维度进行归一化加权。主问题和属于同一主题的追问会先合并，再参与岗位维度聚合；无效轮次不会覆盖此前已经确认的有效主题结果。

最终总分和等级由程序根据有效评估、岗位量规和配置阈值计算，默认等级阈值为 `8 / 6 / 4`。模型生成的文字反馈用于解释表现和给出学习建议，模型自行输出的总分不会覆盖程序计算结果。

## 结果追溯

报告会记录模型名、温度、提示词版本、量规版本、输出 schema 版本和生成时间等信息，便于理解一次报告使用的配置。用量记录单独保存实际已知用量和未知占额，不把缺失的供应商 usage 当作零。

## 评分的适用范围

这套协议解决的是：

- 评分字段是否完整；
- 证据是否来自当前回答；
- 分数换算和岗位维度聚合是否稳定；
- 追问结果能否归并到原主题；
- 报告能否根据同一状态重新计算。

它不证明：

- 模型判断与专家面试官完全一致；
- 分数与录用结果存在统计相关性；
- 不同模型、温度或供应商会产生相同的主观判断；
- 评分可以用于招聘决策、背景调查或能力认证。
